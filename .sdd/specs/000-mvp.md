# SPEC v0.3 — Transpose

> Rebuild any flow in your design system, including the states the screenshots don't show.

Name: like transposing music, the same melody in another key. Here: the same flow in your design system. Packages are scoped: `@transpose/ds`, `@transpose/tokens`, `@transpose/ai`, ...

Status: draft for review. Short sentences on purpose.

## 1. One line

Turn screenshots of any product flow into the same flow built from **your** design system, and find the states the screenshots do not show.

## 2. Problem

- Teams often get only the main screen from design. Loading, empty, error, validation, "what happens after click" are missing. Developers guess. Result: bugs, rework, late questions to design.
- Teams see a good flow in another product (e.g. an onboarding or checkout flow) and want a prototype in their own components. Today this takes days.
- Generic tools (v0, screenshot-to-code) output generic Tailwind/shadcn code, not the team's components. Prototypes get thrown away.

## 3. User

Frontend developer or small product team **with a component library but no full-time designer** for every state.

## 4. How it works (the core flow)

1. Upload 1–5 screenshots in order (one flow).
2. **Analyze** (vision model): each screen becomes a _semantic tree_ — what is there, not which component. Example: `header`, `list of services with price`, `date picker`, `primary action`. Zod-validated.
3. **Review plan** (human approval): user sees the tree, can rename, delete or add elements. Nothing is built before "Build".
4. **Map to DS**: a second step maps the semantic tree to design system components, using tools over the component manifest and docs. Output is a _component tree_ (JSON), validated by zod against the real manifest.
5. **Preview**: live render of each screen + a clickable flow map (screen 1 → "Book" → screen 2).
6. **Missing states**: the model lists states and interactions the screenshots do not show, each with a reason and a citation to DS guidelines. User picks which to generate.
7. **Edit by chat**: "make this button secondary", "add phone field". The model proposes a patch; it shows as a diff card with **Apply / Discard**.
8. **Export**: TSX per screen and Storybook stories per state, generated by **deterministic code**, not by the model.

Why two steps (Analyze, then Map): each step can be tested and evaluated alone, and the vision step does not need to know the DS.

### Retrieval (RAG)

**Where RAG is needed and where it is not.**

- Guidelines and patterns (error display, empty states, content rules, accessibility) are long text. They do not fit in a prompt. **RAG is required** for them (F7).
- The Acme DS manifest (~20 components) fits in a prompt with caching. **RAG is not required** for component lookup at this size. It is required for a large DS (150+ components).
- We decide with data, not by default: the **manifest-vs-RAG eval** maps the same screens with (A) the full manifest in the prompt and (B) top-k retrieved components. It compares mapping accuracy, tokens, cost and latency. Then it grows the DS synthetically (variants up to ~150 components) to find where A breaks. The result is written as a decision.

**How it works.**

- **Sources**: component MDX docs, `guidelines/*.md`, `patterns/*.md`, token descriptions.
- **Chunking**: by heading. One chunk = one heading section, with file path, heading anchor and component name as metadata. STE-style short sentences keep chunks clean.
- **Hybrid search**: pgvector (meaning) + Postgres full-text (exact terms such as `FormField` or `color.action.primary`), merged with reciprocal rank fusion. Embedding search alone often misses exact names.
- **Citations**: file path + heading anchor, clickable in the UI. Every suggestion in F7 has at least one citation, or it is shown as a question for design.
- **Threshold**: below a relevance score, the answer is "not in your DS guidelines". No citation, no claim.
- **Reindex**: a script rebuilds the index when docs change; CI checks the index is current.

## 6. Acme DS

The demo library. Real users plug in their own DS later; Acme proves the tool works on a library the model has never seen.

**Principles**

- **Atomic structure**: tokens → atoms → molecules → organisms → templates. The level is in the folder structure and in the manifest. Rule of thumb: a molecule does one job (one field); an organism is a self-contained section block.
- **No domain in the DS.** Components know nothing about the business. `TimeSlotGrid`, not `BookingSlotPicker`. No business props, no timers or date logic inside a Button.
- **White label.** Components read only semantic and component tokens. A theme is a set of token values. Two axes: brand × mode (light / dark). `<AcmeProvider theme mode>` sets `data-theme` / `data-mode`; a theme can also be passed at runtime as an object and turned into CSS variables. Nested themes allowed. Themes change colors, fonts, type scale, radius, density, shadows, motion — never structure or behavior.
- **Accessibility from day one**: behavior from Radix, axe tests in CI, focus and keyboard tested in Playwright.

**Stack**

- **Radix UI** primitives for behavior (widely used; shadcn/ui is built on it).
- **Tailwind v4 + `cva`** for styles and variants. Tailwind is internal; consumers see only props.
- **Tokens**: JSON in W3C Design Tokens (DTCG) format → **Style Dictionary** → CSS variables (for Tailwind `@theme`), TS types, and JSON for the AI manifest.

**Tokens: 3 layers**

| Layer     | Example                                                             | Used by             |
| --------- | ------------------------------------------------------------------- | ------------------- |
| primitive | `yellow.400`, `space.4`                                             | semantic layer only |
| semantic  | `color.action.primary`, `color.surface.raised`, `color.text.accent` | components          |
| component | `button.padding.x`, `panel.radius`                                  | one component       |

Rules: a component never reads a primitive. No raw colors or px in components or in generated trees. Type sizes in `rem`, headings fluid with `clamp()`. Type roles: `display`, `title`, `body`, `caption`.

**Build check**: every theme × mode is checked for contrast (text ≥ 4.5:1, large text and UI ≥ 3:1). A theme that fails breaks the build.

**Components: two waves**

| Level     | Wave 1 (week 1)                                                      | Wave 2 (weeks 3–5, driven by eval data)             |
| --------- | -------------------------------------------------------------------- | --------------------------------------------------- |
| Atoms     | Text, Heading, Button, Icon, Input, Checkbox, Badge, Avatar, Spinner | IconButton, Radio, Switch, Divider, Skeleton        |
| Molecules | FormField                                                            | SearchField, ListItem, Tabs, DateInput, Toast       |
| Organisms | Panel, Dialog                                                        | Header, ItemList, TimeSlotGrid, EmptyState, Stepper |
| Templates | Centered                                                             | Sidebar, Wizard                                     |

Wave 2 is added when evals show a gap (e.g. "the model built a list from atoms on 6 of 20 screens → add ItemList").

**Lessons from a previous library** (ideas only, no code): keep per-component MDX docs, a component template script, and pinning known bugs with `it.fails` tests in a GOTCHAS file. Do better on: real atomic structure, no domain components, a semantic token layer, rem/fluid type, one styling approach.

## 8. Rules (safety and honesty)

- The model never writes code that ships. It writes JSON; code is generated by our own codegen.
- Nothing changes without a click: plan, patches and new states are proposals.
- Copy structure and flow, not brand: the result uses Acme DS styles only; we do not copy logos, images or text style.
- Screenshots may contain personal data. Demo: warn on upload, delete uploads after 24 h, never log image content.
- Public demo uses our own invented screenshots of common screens (onboarding, profile settings, dashboard, checkout), not real brands.

**Writing standard for all docs.** README, `docs/`, component docs (MDX), DS guidelines, ADRs and specs follow **ASD-STE100 Simplified Technical English** (the aerospace standard for aircraft maintenance documentation) **at about 80%**: we take the writing rules below, not the full standard. We do not use the STE approved dictionary (limited word list) and we do not ban `-ing` forms or common software terms.

- One instruction per sentence. Procedure sentences: max 20 words. Descriptive sentences: max 25 words.
- Imperative mood for instructions ("Use `Panel` for a section block."). Active voice.
- One word, one meaning. Use the same term for the same thing everywhere (keep a glossary in `docs/glossary.md`).
- Paragraphs: max 6 sentences. Lists for steps, in the order the reader does them.
- Put a warning or caution **before** the step it is about.
- No idioms, no slang, no vague words ("simply", "just", "etc.").

Why it matters here: DS docs are also the RAG source. Short, unambiguous sentences give better retrieval and better model answers. A doc lint step (word count per sentence, banned words) runs in CI as **warnings**, not errors. Model prompts in `packages/ai/prompts/` follow the same rules.

## 9. Evals and acceptance criteria

Thresholds are first guesses. We set real ones after a baseline run.

| Eval            | Dataset                                      | Metric                                                                             | Start target             |
| --------------- | -------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------ |
| Analyze         | 20 labelled screenshots                      | element recall / precision                                                         | ≥ 0.85 / ≥ 0.80          |
| Map             | same 20                                      | valid tree after repair; DS rule violations per screen                             | 100% valid; ≤ 1          |
| Visual judge    | same 20                                      | vision model scores original vs result on a checklist (hierarchy, grouping, order) | ≥ 4/5 avg                |
| Missing states  | 15 flows with known missing states           | recall / precision                                                                 | ≥ 0.70 / ≥ 0.60          |
| Export          | all generated trees                          | `tsc` passes                                                                       | 100%                     |
| Quality floor   | the 20 screens, rendered                     | axe violations; touch targets ≥ 44 px; visible focus                               | 0 serious axe violations |
| Retrieval       | 40 questions → correct doc section           | recall@5                                                                           | ≥ 0.90                   |
| Grounding       | 15 questions with no answer in the docs      | "not in your guidelines" returned                                                  | 15/15                    |
| Manifest vs RAG | the 20 screens, DS at 20 and ~150 components | mapping accuracy, tokens, cost, latency                                            | report, no gate          |

Other acceptance criteria:

- First streamed token < 2 s on the live demo. Cancel stops the server call.
- A failed call shows Retry, never a blank screen.
- Nothing is built before "Build", no patch applied before "Apply" (Playwright).
- Every AI call has a row in `ai_calls`.
- `docker compose up` works on a clean machine. Demo cannot spend more than the daily cap.
- `docs/evals.md` is generated by script; CI fails if Analyze recall or Map validity drops.

## 10. Stack (one line why)

- **Monorepo**: pnpm + Turborepo — standard, fast, shared packages.
- **Web**: Next.js App Router + TypeScript + Tailwind v4 — same styling stack as Acme DS.
- **DS**: Radix + Tailwind v4 + `cva`, tokens via Style Dictionary (see section 6).
- **API**: NestJS — the AI pipeline is long (vision on up to 5 screens, mapping, repair: 30–90 s), so it runs on a server with no serverless time limit. An interceptor writes every AI call to `ai_calls`. DI swaps the provider (real, fake for tests and evals). Zod pipes validate every body. Room for a job queue later. Costs about one week and a second deploy. Next.js is UI only.
- **AI**: Vercel AI SDK + Anthropic provider behind a small provider interface. Stronger model for vision/mapping, small model for cheap checks. Exact model ids and prices checked in week 2.
- **Streaming**: SSE over `fetch` POST with **our own typed domain events**, read by a small hand-written client reader (one for all steps, chat edits included). The product is a pipeline of steps, not a chat, so `useChat` (AI SDK chat protocol) does not fit. AI SDK stays on the server (`streamText`, `streamObject`, tools).
  - Events: `step.started`, `screen.started`, `element.found`, `screen.done`, `map.started`, `repair.attempt`, `map.done`, `state.suggested`, `patch.proposed`, `usage`, `error`, `done`. Each has an `id` and a zod schema shared by API and web.
  - Client: `AbortController` for Cancel (the server stops the model call on disconnect), Retry from the last finished step, a clear error state per step.
- **DB**: Postgres + pgvector + Drizzle — one DB for projects, traces and RAG; Drizzle because SQL stays visible.
- **Embeddings**: one hosted provider with a free tier (decide in week 5).
- **Storage**: local disk in dev, S3-compatible bucket in prod.
- **Tests**: Vitest, Playwright, axe for a11y.
- **Deploy**: Vercel (web) + Fly.io or Render (API) + Neon (DB). Free tiers.

## 13. Working process (SDD-lite)

A light version of spec-driven delivery for one developer and AI agents. It replaces Spec Kit. All files are plain Markdown in the repo, so a person and an agent read the same information.

**Flow**

```
/spec  ->  /plan  ->  /implement  ->  /improve (any time)
```

| Command      | Input                                        | Output                                                                                          |
| ------------ | -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `/spec`      | A need or a defect, in one or more sentences | `.sdd/specs/<id>-<slug>.md`: problem, expected outcome, scope, out of scope                     |
| `/plan`      | One spec                                     | `.sdd/plans/<id>-<slug>.md`: behaviour, approach, proof (tests and evals), question ledger      |
| `/implement` | One agreed plan with no open questions       | The change, its tests, updated docs, a pull request                                             |
| `/improve`   | One sentence about the process               | The fix, applied now and written in exactly one place: a check, a rule, a decision or a command |

**Proportion.** The process fits the size of the change.

|              | Small                             | Normal                                            |
| ------------ | --------------------------------- | ------------------------------------------------- |
| Example      | A bug fix, a new token, a doc fix | A feature (F1–F12)                                |
| Spec         | Not needed                        | Needed                                            |
| Plan         | About 12 lines                    | Full plan with question ledger                    |
| Report in PR | 4 lines, and what is not done     | Full, with eval numbers when AI behaviour changes |

**Repository layout**

```
.sdd/
  README.md        index: where to find what
  handbook.md      one page: the flow, Definition of Done, who decides what
  glossary.md      one term, one meaning (semantic tree, component tree, state, flow, ...)
  rules/           conventions with no interesting alternative, written as instructions
  decisions/       choices with a rejected alternative (ADR format), never deleted
  specs/  plans/   one file per delivery item
  reference/rules-enforcement.md   each rule -> the check that holds it, or "review only" and why
.claude/
  commands/        spec.md, plan.md, implement.md, improve.md
  agents/          repo-explorer, claim-checker, reviewer-agent
CLAUDE.md          short; points to .sdd/rules instead of repeating them
```

**Rule or decision.** The test: was a choice made?

- Rule: "Variants use `cva`." No real alternative was weighed.
- Decision: "Analyze and Map are two separate steps." An alternative was rejected and it has consequences.
- A rule can state a constraint from a decision. It links to the decision and does not repeat the reasoning.

**Decision format**: title as a statement; header list with Status (Accepted, `Superseded by <slug>`), Date, Spec id; then Context, Decision, Alternatives considered, Consequences (Positive, Negative), Conditions for review, See also. A reversed decision is marked superseded and a new one is written.

**First decisions to write** (week 1): two-step pipeline (Analyze, then Map); the model writes JSON, code comes from codegen; Radix over Base UI; NestJS API over Next.js Route Handlers; tokens in DTCG + Style Dictionary; own typed SSE events over AI SDK `useChat`; a simple `ai_calls` table over Langfuse first.

**Checks, not hooks.** Every rule a tool can decide is checked in CI, with no exemption (no `eslint-disable`, no `@ts-ignore`, no ignore lists). No git hooks. `pnpm check` runs the same gates as CI, cheapest first, and stops at the first failure. Coverage target is per package and realistic, not 100% everywhere.

**Subagents** (each file names its model and effort):

- `repo-explorer`: read-only, cheap model. Maps what exists, with `path:line` citations.
- `claim-checker`: read-only. Checks the claims in a plan, a review or a doc against the code. Returns a verdict per claim with evidence.
- `reviewer-agent`: independent review of a draft pull request it did not write.

**Precedence.** A rule outranks habit and existing code. A plan cannot quietly waive a rule; it names the rule, the reason and for how long. Two rules in conflict is a defect: apply the more specific one and raise it with `/improve`.

**Not taken** (too heavy for one person): ticket tracker integration, separate Product and Engineering sign-offs, release verification stage, hotfix flow, moving released plans, 100% coverage per module.
